# Prerequisite installation specification

This specification defines the bootstrap and prerequisite installation flow
for mdview development environments. The goal is to supply a predictable way
to set up system packages and Python dependencies across Rocky Linux 9.6,
Fedora 43, Ubuntu 24.x, Linux Mint, Debian (current stable/testing), recent
macOS versions, and Windows 11.

## Objectives
- Provide a canonical shell entry point (`install.sh`) that can run on
  minimal Unix-like systems, ensure a working bootstrap interpreter, and
  invoke the managed stage-two installer safely.
- Keep `bootstrap.sh` and `scripts/install_prerequisites.sh` as compatibility
  wrappers to `install.sh`.
- Implement `scripts/install-stage-2.py` as the managed stage-two installer
  that detects install mode/scope, provisions bootstrap/runtime pyenv
  contexts for repo-local development, refreshes `.venv`, and installs
  managed hooks.
- Keep mdview-specific install behavior in `scripts/install_project.py`,
  including project package installation and launcher management.
- Track bootstrap/runtime pyenv contexts through `python-environments.json`,
  `.python-version`, `set-context.sh`, and `set-context-bootstrap.sh`.
- Ensure repo-local development refreshes the pinned local-check tools through
  `scripts/dev_setup.py`.
- For interactive developer installs, prompt whether typing `mdview` outside
  the checkout should resolve to the local development copy or to another
  installed copy, and report whether another `mdview` executable appears on
  the current PATH before asking.
- Keep logic compatible with Python 3.9+ in bootstrap/setup paths and avoid
  non-portable shell features.
- Ensure repository launchers invoke mdview's internal CLI and never depend
  on external renderers such as `pandoc` or GUI openers.

## System package expectations
- Debian/Ubuntu/Mint: install `python3`, `python3-venv`, `python3-pip`,
  and `git` using `apt-get update` + `apt-get install -y`.
- Fedora/Rocky: install `python3`, `python3-pip`, `python3-virtualenv`,
  and `git` using `dnf` or `yum` depending on availability.
- macOS (Homebrew): install `python` and `git` with `brew update` +
  `brew install`.
- Windows 11: use `py -3` (or `python`) and skip system package-manager
  installation in this script path; bootstrap directly into virtualenv and
  pip installation.

## Virtual environment strategy
- Use `install.sh --mode dev` as the canonical direct-checkout development
  bootstrap entry point.
- Let `install.sh` default to a user-local non-development install in
  standard mode, while `--mode dev` and `--mode venv-only` remain repo-local.
- Use `scripts/install-stage-2.py` to provision the configured pyenv
  bootstrap and runtime selections and to write `.python-version` to the
  runtime selection for repo-local development.
- Use `.venv` at the repository root for development and venv-only modes.
- Resolve project root independently of caller working directory so the
  installer can run from subdirectories such as `scripts/` and still install
  from repository root.
- Upgrade `pip`, `setuptools`, and `wheel` inside managed virtual
  environments before project or tool installs.
- Install the project in editable mode with `interactive` extras for
  development and non-editable mode for standard installs.
- Refresh the pinned Black/Ruff/pytest toolchain through
  `scripts/dev_setup.py` for development and venv-only modes.
- Repository-local checks must run with `.venv/bin/python` or an activated
  `.venv` so the development environment remains authoritative.

## Safety and usability
- Prefer `sudo` only for explicit `./install.sh --system` installs.
- Reject `sudo ./install.sh` without `--system`.
- Reject `./install.sh --system` when the current process is not running as
  root.
- Skip package-manager installation when the required bootstrap tools are
  already present on the host.
- When running interactively in development mode, report whether a
  non-checkout `mdview` executable appears on PATH before prompting about
  command resolution.
- If the developer chooses the local checkout, install a managed user-local
  dev launcher that delegates to the checkout `.venv` entry point.
- If the developer chooses the non-development path, restore a managed
  standard launcher when one was displaced by the dev launcher and otherwise
  leave PATH resolution unchanged.
- Never overwrite an unrelated existing `mdview` executable silently.
- When an unmanaged existing `mdview` launcher blocks a managed install, end
  the refusal output with:
  `Use --force if you really want to overwrite your existing installed copy`
  `at <directory>.`
- `--force` must explicitly allow standard or development installs to replace
  that existing installed copy in the target launcher directory.
- Fail with clear messaging when the platform is unsupported or required
  tools are unavailable.

## Testing considerations
- Expose pure functions for parsing `/etc/os-release`, mapping package
  managers, and building install commands so pytest can cover decision
  paths without invoking subprocesses.
- Cover PATH probing, prompt selection, managed launcher creation, managed
  standard-launcher restore, and venv-only no-op behavior without touching
  the real user environment.
- Keep subprocess calls isolated behind a runner utility that can be
  stubbed in tests.
