Problem Statement
-----------------
mdview currently lacks a formal, source-agnostic internal document object
model that can carry both fidelity data and behavior metadata across intake,
policy, rendering, and viewing layers. Without a shared model, reflow and
scrolling behavior become fragmented and difficult to reason about when files
contain mixed structures such as prose, fixed-width tables, and list blocks.

Goals
-----
- Define a unified document object model (DOM) for all input sources.
- Preserve source fidelity, including line-boundary intent and text order.
- Represent block-level probabilities, hard limits, and soft behavior hints.
- Provide a stable interface for parser, renderer, and viewer collaboration.

Non-Goals
---------
- Implementing parser algorithms or viewer event loops in this proposal.
- Finalizing performance optimizations beyond required guardrails.
- Defining every style-specific renderer rule in this proposal.

Use Cases
---------
- A ``.txt`` document with mixed prose and fixed-width ASCII tables needs
  selective reflow without corrupting tables.
- A Markdown document includes wide tables and normal paragraphs; viewer must
  respect overflow while still reflowing prose.
- A future format is added and must plug into existing policy and viewer logic
  through shared interfaces.

Constraints and Assumptions
---------------------------
- Python 3.9+ compatibility and low startup overhead are required.
- DOM must remain serializable for diagnostics and reproducible tests.
- DOM operations must preserve character order and avoid hidden mutations.
- External display tools (``less``, ``more``) are out of scope.

Proposed Approach
-----------------
- Define core objects:
  - ``Document``: ordered block list, document metadata, aggregate stats.
  - ``Block``: ordered line spans, classification score vector, constraints.
  - ``Line``: source text, normalized text, width metrics, break markers.
  - ``ConstraintProfile``: hard limits and soft hints for behavior.
  - ``StyleProfile``: semantic style/type metadata for rendering.
- Encode constraints as explicit contracts:
  - Hard limits: no-reflow, minimum width, preserve indentation.
  - Soft hints: preferred wrap mode, preferred anchor behavior, scroll bias.
- Require all downstream systems to consume DOM contracts rather than infer
  behavior from raw text post hoc.
- Add a schema-oriented debug export for deterministic test assertions.

Risks and Mitigations
---------------------
- Risk: Model complexity slows adoption.
  Mitigation: Start with minimal required fields and versioned extensions.
- Risk: Conflicting hints across layers.
  Mitigation: Define precedence: hard limits > policy mode > soft hints.
- Risk: Overfitting to current content types.
  Mitigation: Keep types extensible and score vectors open-ended.

Testing and Validation
----------------------
- Build unit tests for model invariants, serialization, and precedence logic.
- Add fixture-driven tests that verify hard-limit enforcement for mixed
  blocks.
- Validate integration contracts between parser output, renderer input, and
  viewer behavior. Follow Joel Spolsky's ship-readiness expectations by
  requiring broad edge-case coverage before rollout.

Alternatives Considered
-----------------------
- Continue with ad hoc structures per subsystem.
  Rejected because it blocks consistent policy enforcement.
- Use a single flattened line list without block objects.
  Rejected because block-aware policies cannot be applied reliably.

Open Questions
--------------
- Should style metadata live on blocks, spans, or both? Owner: Architecture
  team. Decision by: 2026-03-21.
- Which debug export format should be canonical (JSON vs compact text)?
  Owner: Tooling lead. Decision by: 2026-03-21.

Milestones
----------
- Milestone 1 (2026-03-14): Finalize DOM schema and precedence contracts.
- Milestone 2 (2026-03-21): Implement core objects and serialization.
- Milestone 3 (2026-03-28): Integrate parser and viewer adapters.

Adoption and Rollout
--------------------
- Introduce DOM behind a compatibility layer that can mirror current behavior.
- Gate rollout through fixture-based comparisons against existing rendering.
- Promote to default once parser and viewer consume DOM contracts end to end.
